The crew

How the crew works

You stay in one conversation. Each specialist has its own tools and instructions, and hands the task across when the work changes.

  1. 01

    Architect

    Weighs trade-offs and writes the approach before a line of code.

  2. 02

    Coder

    Picks up the handoff with that context and implements it, using its own tools.

  3. 03

    Reviewer

    Checks the result, sends fixes back, and approves when it holds.

The handoff

/agent switches who you are talking to. @Name hands a subtask to another agent, with the conversation’s context. Names are the agents in your crew. 

/agent Architect
Design the approach.

@Coder Implement the plan.

@Reviewer Review the result.

What persists

The crew keeps what it learns

Four parts of AgentCrew outlive the chat. Each film is silent, about half a minute, and plays when it scrolls into view.

01 Memory

It remembers the job, per agent.

After every turn, a background worker turns the chat into a structured memory. Memories are saved locally in SQLite at ~/.AgentCrew/memory.db, scoped to that agent, and kept across sessions.

Next session, the relevant memory comes back with the agent. The Architect’s decision does not automatically become the Coder’s — say it again in the handoff if the next agent needs it.

How memory is scoped

02 /learn

Teach a rule once.

A behavior is a simple rule: when this happens, do that. /learn reads the current conversation and proposes rules. You confirm each one — global, or this project — or you skip it.

Confirmed behaviors live in ~/.AgentCrew/persistents/adaptive.json and apply when the condition matches, including on later sessions.

Adaptive behaviors

03 /evolve

The system prompt can improve itself.

/evolve studies an agent’s memory and proposes a revised system prompt: durable traits and output preferences. It starts with three optional questions about how you want that agent to work.

Nothing changes until you accept, edit, or decline. The proposal is a review, not a silent rewrite.

Command reference

04 craft_skill

Save a workflow as a skill.

Ask an agent to keep a workflow you repeat. craft_skill writes a skill — instructions plus at least one script — into the project’s .agents/skills folder. Scripts can be Python, Bash, PowerShell, or JavaScript.

It checks and saves the skill; it does not run the script. Crafting is offered on a trusted project, to agents that can run commands and edit files. Three skills stay active at once; a fourth sets the oldest aside.

Models you already have

Supported providers

Pick a provider. Model catalogs move; the sign-in does not. Pass --model-id when you want a specific model, or switch later with /model.

Subscription, no API key

  • xAI agentcrew xai-auth then --provider xai
  • ChatGPT Plus / Pro agentcrew chatgpt-auth then --provider openai_codex
  • GitHub Copilot agentcrew copilot-auth then --provider github_copilot
  • OpenCode Go agentcrew chat --provider opencode_go
  • Command Code Subscription

API key

  • OpenAIPer-token
  • AnthropicPer-token
  • Google GeminiFree tier available
  • DeepInfraPay as you go
  • Together AIPay as you go
  • FireworksPay as you go
  • RefuselessAPI key

Set a key in the environment, or under api_keys in ~/.AgentCrew/config.json.

On your machine

Ollama, llama.cpp, LM Studio, and other OpenAI-compatible endpoints are custom providers in ~/.AgentCrew/config.json. Fully local, including air-gapped machines.

Cursor Agent is a supported agent type for editing the repository you are in. Files stay on your machine; inference is hosted by Cursor. Set CURSOR_API_KEY, then add a [[cursor_agents]] entry.
